# 对比结果：XHarness 对上游 DeepSeek Harness

**日期：** 2026-09-17
**题目：** Terminal-Bench 冻结集 47 题（`frozen/tier-a-plan.json`）
**模型：** `deepseek-v4-flash`，经 `https://api.deepseek.com`
**两臂上下文窗口：** 均 1,000,000（见 T16）
**两臂单步输出上限：** 均 32,768（见 T18）

---

## 一句话结论

**这个规模测不出两臂的差异。** 配对不一致只有 5 对，McNemar 精确检验 p = 1.0000。
要把"谁更强"作为结论说出口，需要 194 题（分辨 10 个百分点）或 783 题（分辨 5 个百分点）；
这里只有 37 题可比。

---

## 数字

| 臂 | 版本 | 通过 | 未判定 |
| --- | --- | ---: | ---: |
| XHarness | 0.2.19（复刻 `dsh-v0.1.0-rc.8`） | 35/47 = 74.5% | 0 |
| 上游 | SDK `0.1.0rc7` | 34/43 = 79.1% | 4 |

Wilson 95% 置信区间：XHarness `[60.5%, 84.7%]`，上游 `[64.8%, 88.6%]` —— **大面积重叠**。

上游那 10 个原本"未判定"的 trial 补跑后：**7 个通过**（它们之前被算作失败，实际上从未
运行过 —— 装包超时，已修 `--offline`），3 个撞 1,800 秒上限，1 个是 agent 自己写的脚本
在验证器重跑时挂住。

**上游那 3 个超时里有 1 个不公平**：`compile-compcert` 上 XHarness 用 1,623 秒做完并通过，
上游撞到 1,800 秒上限。**这道题计入"只有 XHarness 通过"，但那不是能力差异，是上限差异**
（见 T26）。上游的 79.1% 因此是下界而非测量值。

### 配对（两臂都被判定的 43 题）

| | 题数 |
| --- | ---: |
| 都通过 | 31 |
| 都失败 | 6 |
| 只有 XHarness 通过 | 3 |
| 只有上游通过 | 3 |

**3 比 3，完全对称。不一致 6 对 → p = 1.0000。**

XHarness 独有：`extract-elf`、`kv-store-grpc`、`torch-tensor-parallelism`
上游独有：`cancel-async-tasks`、`dna-insert`、`llm-inference-batching-scheduler`

不一致里任意一题翻转，"谁赢"的叙述方向就变。这就是 p = 1 的含义 ——
不是"两者相同"，而是**这个规模无法区分**。

数字可用 `scripts/compare.py` 复现：

```bash
scripts/compare.py \
  --arm xharness-1M=runs/tier-a3-xharness \
  --arm upstream=runs/tier-a2-dsh --arm upstream=runs/tier-a2-dsh-retry \
  --baseline upstream --candidate xharness-1M
```

## 次要发现（这些比胜负更确定）

### 耗时：XHarness 慢约 2.4 倍

| 臂 | 中位 | 最长 |
| --- | ---: | ---: |
| XHarness | 470 s | 1802 s |
| 上游 | 224 s | 1556 s |

这个差异**不依赖统计检验**：中位数差 2.1 倍，样本 43 对，远超噪声。

**注意**：两臂都被 1,800 秒的 agent 上限截断（见 T25），所以"最长"那一列是上限而不是
实际需要的时间。`extract-moves-from-video` 两边都撞到它。

### 提示词规模：XHarness 每步更重，但步数更少

在两臂都通过的题上，XHarness 每步提示 token 普遍更高（`git-multibranch` 13,758 vs 4,842；
`bn-fit-modify` 8,474 vs 3,320），但总步数更少（`fix-ocaml-gc` 57 步 vs 248 步），
所以长任务上总 token 反而更低。

缓存命中率两臂相同（94–99%），不是缓存策略的差异。

### 未解释的异常：`max-tokens` 结局 11 次 vs 4 次

两臂每次请求都带相同的 `max_tokens`，每步推理量分布基本对称
（XHarness 更多的 19 题，上游更多的 18 题），但 XHarness 有 11 个 trial 以 `max-tokens`
结束、上游只有 4 个。**没有找到机制，记录为待查，不作为结论。**

## 这个对比测了什么，没测什么

**测了：复刻保真度。** 两臂在契约层面大致等价（`0.1.0rc7` 对 `rc.8`，
2026-08-21 的增量审计显示固定 RPC 名称集合无变化），所以差异反映的是实现差异。

**没测：今天的上游。** 上游此后发布了 16 个 tag（到 `dsh-v0.1.6-alpha.1`），
包含会话格式 V3、`ApiProxy` 移除、默认协议改 Messages 等破坏性变更。
完整情况见 [version-drift.md](version-drift.md)。**结论只对 `0.1.0rc7` 成立。**

**没测：真实竞争格局。** 43 道配对题里 31 题两臂都过、6 题都败 —— **86% 的题零区分度**，
只有 6 对不一致。见 [T23](validity.md)。

**而且那 6 对里至少 1 对不是能力差异。** `compile-compcert` 的差别来自 1,800 秒上限
（T26），不是 harness。去掉它，不一致降到 5 对，仍然是 3:2 附近 —— 无论如何都测不出。

## 读这份报告时要知道的前提

这个 bench 从第一次运行到现在，修掉了 22 个会歪曲结果的问题，其中**每一个都曾产出一个
看起来合理的错误数字**。最重要的几个：

- **T14/T16/T18** —— 上下文窗口和输出上限。两臂一度拿到差 8 倍的窗口，
  一次控制实验（只改预算）让同一批题从 0/3 变成 2/3。
- **T19** —— 适配器只读了每次会话的最后 50 条消息，却当作全部统计。
- **T21** —— 工具调用计数器把 `tool/result` 也算作调用，所有历史数字虚高约 2 倍。
- **T22** —— 测量代码和它的测试按同一个错误假设写，12 项断言全绿而数据全是空的。

完整清单在 [validity.md](validity.md)。**任何一项都足以让"74.5% 对 75.7%"变成噪声。**

## 建议

1. **不要引用这两个百分比作为胜负。** 要下结论需要 194+ 题。
2. **可以引用耗时和每步 token 的差异** —— 那些是 2–3 倍的量级，不是 2 个百分点。
3. **若要用作产品决策**，需要一条跑当前上游的臂（`--ak sdk_version=latest`），
   外加一个分辨率足够的题集。
